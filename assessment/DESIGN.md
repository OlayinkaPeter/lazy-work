# Donor audience service

## Scope and architecture

The objective is fewer unnecessary emails while retaining at least 100% of BAU's estimated donations **and** dollars. A model's AUC does not establish that outcome. I use the supplied centroid-cosine ranking, select its operating point on historical campaigns, and gate publication on an independent time holdout. I do not retrain a more complex model for this submission. This is an explicit baseline policy, not a claim of prediction parity with the fitted logistic regression, especially for missing engagement.

One FastAPI process accepts requests; one worker thread consumes a durable SQLite queue. Both run in one container with a 2 GiB memory limit and four CPUs. SQLite WAL/FULL synchronization and a process file lock prevent concurrent workers sharing this state. Several requests can queue without loading multiple copies of the scoring data. Kafka/Celery/Redis would add services and failure modes without helping this request volume.

Nightly, after the warehouse's 01:00 America/New_York watermark is available, `prepare` reads active people and distinct recent engagements using DuckDB, with a 1 GB query memory budget. It writes an immutable, hash-checked artifact version and atomically updates `CURRENT` only after loading and validating it. There is an eight-hour preparation window before staff start. Policy calibration is a separate release operation, not something to retune every night using the same holdout. The CLI defaults to the supplied simulated snapshot; production must supply the actual completed warehouse watermark.

At request time the API validates the organization, audience type, program area, finite 1024-dimensional embedding and timezone. It records an idempotent job and returns 202 with a status URL. The worker pins the current artifact, scores eligible people, deterministically selects the policy's top share, persists that audience, then calls the CRM once. Repeated identical request ids return the original job; conflicting payloads get 409. Queue saturation returns 429. Missing/stale snapshots return 503; queued jobs also recheck freshness and fail before delivery if necessary. There is no random-audience fallback.

Render's background worker does not provide public HTTP ingress. The local equivalent is a web container with a background scoring thread; a real Render deployment would use a private/authenticated web service on equivalent resources and a persistent disk, or separate ingress and worker with a shared durable database. This implementation does not pretend two independent containers can share a local SQLite volume across hosts.

## Memory and latency budget

The dense centroid approach costs `250,000 * 1024 * 4 = 1,024,000,000` bytes (977 MiB) for just one float32 matrix. Temporaries and concurrent requests threaten the hard limit.

Instead let B be a binary people-by-historical-content sparse matrix, E the 52-by-1024 content matrix, and q the normalized request embedding. The centroid's averaging factor cancels in cosine:

`score(p,q) = B[p] @ (E @ q) / sqrt(B[p] @ (E @ E.T) @ B[p].T)`.

We precompute the denominator, using the tiny Gram matrix one column at a time, without forming B @ E. Missing or zero-norm engagement receives score -2; valid cosines are in [-1,1]. Ties use a deterministic integer hash of person id, shared between backtest and service, so signup-order ids do not systematically win. This preserves the starter's distinct-content/first-engagement semantics and 30-day, left-inclusive/right-exclusive window.

For 250k people and nine engagements each, float32/int32 CSR values/indices cost about 17.2 MiB plus 1 MiB row offsets. Ids cost 1.9 MiB, norms 1 MiB, and E 208 KiB. Scoring needs small content and people vectors; sorting and selected ids use a few more MiB. There is no n_people-by-1024 temporary. An old snapshot may coexist with a new one while a job completes, so budget for two artifact versions. Keep the Python/scipy/API runtime, request objects and CRM list/string conversions within a conservative 512 MiB serving budget; the constrained benchmark supplies actual measured peaks.

Each request performs about 53k embedding multiply-adds plus one operation per sparse entry, sorting 250k scores, durable local writes, and the CRM's two-second delay. Use a 10-second per-job planning budget. Eight outstanding jobs therefore have an 80-second planning envelope; that is capacity planning, not a worst-case proof for arbitrary disks or CRM stalls. A worker rejects jobs with less than five seconds remaining before starting delivery. Deadlines use server receipt time, including validation, loading, queueing and delivery; caller timestamps cannot extend them. Success records whether delivery actually met 180 seconds. The mock has bounded latency; a real CRM adapter needs an explicit network timeout and an idempotency key.

## Audience selection and evidence

Historical sends were random 75% samples. Replay the policy on eligible historical sends and compare retained donors, attributed dollars and unsubscribes against 0.75 times the corresponding full observed totals. The seven-day attribution window is left-inclusive/right-exclusive. Outcomes after the snapshot are excluded. Historical eligibility comes from actual sends, not today's active-only survivors.

`evaluate` replays complete eligible campaigns using bounded sparse computations, rather than relying only on the supplied 60k sample. Pre-August campaigns choose the smallest fraction, in one-percentage-point steps from 25% to 100%, that retains at least 105% of estimated BAU donors and dollars. The extra five percentage points are a calibration margin, not a statistical guarantee. August is an untouched final holdout: both ratios must be at least 1.0 and unsubscribes must decrease, or the policy is unapproved and `prepare` refuses to publish it. There is no automatic threshold adjustment after looking at the holdout. Two thousand campaign-level bootstrap samples produce descriptive 95% intervals; few holdout campaigns limit their reliability. Report those intervals, absolute outcome counts and variation across campaigns alongside the aggregate.

For context only, the supplied README reports top-75% centroid targeting at about 108% of BAU donors, 108.3% of dollars and 1.9% fewer unsubscribes. Top-50% gives about 87.7% of BAU donors, 84.9% of dollars and 42.5% fewer unsubscribes. The latter conflicts with our chosen retention requirement. These are supplied sample results, **not** measurements of this implementation. I will not claim our selected share or financial lift until the real backtest runs. At present the warehouse hostname is blocked by the cloud network proxy; the added allowlist rule is saved but has not taken effect in the running machine. See evidence/README.md for the exact validation boundary.

A single global share is deliberately easy to explain. It may still lose donations within a particular program area, and aggregate retention is not a guarantee for each request. A live randomized holdout is needed to validate the business outcome and longer-term list health. History supports a one-send estimate, not a six-month causal forecast of retained subscribers or future donations.

## Persistence, failure modes and operations

Persist immutable scoring versions with checksums, source watermark and calibrated policy; SQLite request fingerprints, states and timestamps; exact selected audience files; and CRM output/receipt metadata. This allows repeated requests to resolve identically, audits to identify the input version and operators to reconcile ambiguous delivery. No credentials are stored. State and CRM outbox use separate persistent volumes. Keep old artifacts while jobs reference them; introduce explicit retention and encrypted backups for a real deployment. This small submission does not implement automatic disk cleanup.

On restart, interrupted scoring returns to the queue, still subject to its original deadline. Interrupted delivery becomes `delivery_unknown`. The mock CRM has no external idempotency key or transactional relationship with SQLite. A crash after CRM creation and before recording its id cannot be made exactly-once locally. Automatically retrying could duplicate a list, so we preserve uncertainty and require reconciliation against outbox files. A production CRM should accept an idempotency key or expose a lookup by our request id. CRM exceptions are treated as uncertain for the same reason. Storage failures make the worker unhealthy; recovery reconciles durable in-progress states before resuming claims.

Artifacts expire after 26 hours of warehouse time; a failed overnight refresh therefore blocks staff rather than silently using yesterday's audience. The fixture replay clock is explicit, observable and separate from deadlines. A real warehouse's daily active status can still miss same-day unsubscribes or bounces. Before a real send, integrate a live suppression check at the CRM/send boundary; with only the supplied snapshot, this system can guarantee eligibility only as of that snapshot. It must not claim legal or operational suppression completeness between refreshes.

Monitor end-to-end p50/p95/p99 and deadline misses, queue depth/oldest age, failed and uncertain jobs, worker health, snapshot age, refresh duration, RSS/cgroup peaks, disk space and CRM latency. Alert on stale artifacts, any ambiguous delivery, increasing backlog, or SLO breaches. Audit each selected list for unique active ids. Run a prospective randomized BAU holdout and measure donations, dollars and unsubscribes with complete attribution windows; also track program-level outcomes, bounce rates, frequency and longer-term subscriber value. The API is a single-tenant demo behind a trusted gateway, not a public authenticated multi-tenant product.

With more time: restore real-data validation first, integrate live suppressions and CRM idempotency, add retention/backup tooling and refresh scheduling, and then test better donation/churn tradeoffs and frequency caps. Keep the service small until measured load or operational requirements justify another queue or database.
